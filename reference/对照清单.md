### I1. 先把截图的缩放比标定死（之前靠目测是错的）

`17-TV-收藏条真实尺寸-2026-10-21.png` 是 **2821×2044** 的截图。原始像素除以 2 才是 CSS 像素，依据三条互相独立、结论一致：

| 判据 | 实测 | 结论 |
|---|---|---|

## K. 第 15 轮：Bar Count 卡顿 /「不跟」

用户反馈：「那个 Bar counter 的数字，现在有很多 bug……现在又卡了，有时候又不跟，我也不知道为什么。」

### K1. 根因不是画得慢，是两个渲染循环差一帧

旧实现把数字画在我们自己的 `#drawLayer` canvas 上，由**独立的 `requestAnimationFrame`** 驱动；
K 线画在 lightweight-charts 自己的 canvas 上。两套循环各跑各的，拖动/缩放/回放时数字永远比 K 线慢一帧 ——
视觉上就是"脱影、不跟"。局部优化（跳帧、缓存坐标）都修不掉这个性质问题。

### K2. 解法：做成 series primitive，进库的渲染管线

`js/chart.js`：

- `drawBarCounts(target)`：在 `target.useBitmapCoordinateSpace(scope => ...)` 里画，
  拿到的是**和 K 线同一块 canvas、同一套坐标**
- `BarCountView = { zOrder:'top', renderer() }`
- `BarCountPrimitive = { attached / detached / paneViews / updateAllViews / refresh }`
- `init()` 里 `this.candle.attachPrimitive(BarCountPrimitive)`
- 重画入口 `ChartMgr.refreshBarCount()` → 图元的 `requestUpdate`

`js/draw.js` 删掉 `drawBarNumbers()`（40 行）与 `render()` 里的调用；`toggleBarCount()` 改调 `refreshBarCount()`。
`js/app.js` 的 `#indBarCount` 同样改调 `refreshBarCount()`。

同一块 canvas ⇒ 天然同帧，不需要任何帧同步手段。

### K3. 两个必须知道的细节

1. **`paneViews()` 必须返回固定数组**。库内部用 `===` 做引用相等比对来决定是否复用视图；
   每次 return 新数组会让它白走一遍视图重建。
2. **上下边界都要判**。旧版只判 `y > H`，K 线跑到视窗上方时数字会飘在顶部；
   现在 `y < 0 || y > H - 12` 都跳过。另外 TV 是纯色字，不描边，只 `fillText`。

### K4. 实测证据

- canvas 归属（遍历所有 canvas 数橙色像素）：
  `[{i:1, w:1000, h:762, orange:2608, ink:758420}]`
  → 橙色数字 2608px 与 K 线墨迹 758420px 在**同一块** canvas。
  （只取 `#chartMain canvas` 会拿到 canvas #0 = series 之前的背景层，橙色为 0，容易误判"没画出来"）
- 拖动帧率 ABBA（BarCount 开/关各 2 轮交替）：`ON avg 16.7 / p95 17.5` vs `OFF avg 16.7 / p95 17.5`
  → **零差异，稳定 60fps**，图元本身不构成负担。
- 帧级「跟不跟」（hook `fillText`，按住鼠标拖 26 步、未松手时截图）：

  | 指标 | 值 | 含义 |
  |---|---|---|
  | rAF 帧数 | 94 | 拖动全程 |
  | 图表重画次数 | 28 | 图表是事件驱动，不是每帧都重画 |
  | **重画了却没画数字的帧** | **0** | 只要重画就一定带数字 → 不会闪 |
  | 每次重画画的数字个数 | 14 ~ 21 | 与可见偶数根数吻合 |
  | 数字平均 x | 277 → 179（25 个不同取值） | 每帧都在跟着平移，不是定格 |

  判据说明：图表每次重画都会画坐标轴刻度（也是 `fillText`），所以
  「这一帧有 `fillText` 但一个 Bar Count 都没有」才等价于"图元被跳过"；
  「这一帧一个 `fillText` 都没有」只是图表没必要重画、画面维持上一帧，属正常。

### K5. 稀疏分级

| `barSpacing` | 间隔 |
|---|---|
| ≥ 5 | 每 2 根 |
| ≥ 3.2 | 每 4 根 |
| ≥ 2 | 每 8 根 |
| < 2 | 不画 |

### K6. 回归断言调整

原断言 hook `fillText` 后调 `Draw.render()` 抓数字；迁进图元后 `Draw.render()` 不再画数字，断言必挂。
改成 `ChartMgr.refreshBarCount()` + `await` 两个 `rAF`，并把取值限定 `1..400` 排除坐标轴上的纯数字刻度。
**103/103 全过**。

### O2. 拖价格轴时止盈止损只在松手后到位

**根因**：lightweight-charts 只对外发「可见逻辑范围」（横向）变化；
在价格轴上上下拖、或滚轮改价格区间，**没有任何订阅回调**。
我们的绘图层（入场/止盈/止损/已画图元）全靠 `subscribeVisibleLogicalRangeChange` 触发重绘，
所以纵向变化时它一帧都不重画 —— 表现就是「不跟手，松手才一次性跳到位」。

**做法**（`draw.js → watchPriceScale()`）：
每帧取两个固定价格（0 和 100）在屏幕上的 y 当指纹
（缩放改斜率、平移改截距，两个采样都看），指纹变了就补一帧 `render()`；
`yOf/pOf` 本来就每次现算，所以重绘即跟随。

为了不白烧 CPU，**只在交互窗口内跑**：
`mousedown` 起跟 15s（按住期间一直跟）、`mouseup` 立刻收成 250ms 收尾、
`wheel` 后 320ms、`dblclick` 后 400ms。静止时没有 rAF 循环。

**顺带修的真 bug**：交易线的命中判定只看 y 不看 x，点在右侧价格轴上、
高度正好和某条线相同时会被当成拖那条线（而不是平移/缩放价格轴）。
`onDown` 里加了一条：`x > W - axisWidth` 的手势一律让给图表库。

实测：按住价格轴下拉 70px，**松手前**绘图层已重绘 10 次，TP Δ0.5px、SL Δ−17.3px
（价格轴拖动在库里的语义是「纵向缩放」，不是平移，所以两条线位移量不等），
而 `Trading.tp/sl` 的价格值一个都没变 —— 证明只是视图在跟，没有误改订单。

### Q11. 「一直在后台启动服务器」查出的真问题：进程泄漏（已修）

用户问起后台服务器，顺手一查发现 **19 个 `pythonw.exe` 全是 `es-replay\server.py`**，
而 `Get-NetTCPConnection` 显示只有 **8899 一个端口在监听** —— 其余 18 个是空转僵尸。

**根因**（Windows 语义陷阱）：

```python
# 旧 pick_port(): 试绑时开 SO_REUSEADDR
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(('127.0.0.1', p))     # Windows 上「已占用」也不报错 → 永远返回 8899
```

Linux 的 `SO_REUSEADDR` 只放行 `TIME_WAIT`；Windows 的语义是**允许抢占已被 listen 的端口**。
于是 `pick_port()` 永远给 8899，`ThreadingHTTPServer` 默认也开着 `allow_reuse_address`，
每双击一次 `启动.vbs` 就多一个永不退出的服务进程。

**四处修改**：

1. `pick_port()`：Windows 改用 `SO_EXCLUSIVEADDRUSE` 独占探测，占用就换下一个端口
2. `Server(ThreadingHTTPServer)`：`allow_reuse_address = os.name != 'nt'`，别再抢占
3. `server.py` 启动时先 `already_running()` 探活 —— 已有实例就**直接 return 退出**，
   不占端口、不覆盖 `port.txt`（日志记 `already serving on 8899, skip this instance`）
   —— 这层是兜底，因为安全策略禁止我在本机执行脚本宿主，`启动.vbs` 那句没法自动验证
4. `启动.vbs`：启动前先 `GET /__ping` 探活，有人在跑就**只开浏览器、不再拉进程**；
   `server.py` 相应加了 `GET /__ping` 返回 `ok`（`do_GET` 只拦这一个路径，其余仍走 `super().do_GET()`）

另给启动器加了可选开关 `wscript 启动.vbs /nobrowser`：只起服务不开浏览器，方便自查。

**实测**：

```

ping     = ok
=== 实例 2: 重复启动 ===
存活进程数 = 1
server.log: already serving on 8899, skip this instance (pid 36296)
```

清掉 17 个僵尸后只剩 1 个在服务；静态资源 `/ /index.html /css/app.css /js/app.js /data/meta.json` 全部 200。

### R4. 为什么一定要先起服务（本轮只解释，没改代码）

浏览器打开本地页面只有两条路：

1. **双击 `index.html`（`file://` 协议）** —— 页面能显示，但**读不到行情数据**
2. **通过 `http://127.0.0.1:8899`（本地服务）** —— 正常

原因是这个工具的数据不是写死在 JS 里的，而是运行时按需拉：

```js
const r = await fetch('data/meta.json?_=' + Date.now());     // 索引
const resp = await fetch(url);                               // data/rth_5m/2024.bin.gz
new DecompressionStream('gzip')                              // 现场解压
```

- `file://` 下浏览器给每个文件单独一个「null 源」，`fetch()` 读本地文件直接被 CORS 拦掉；
- 我们的请求还有 `/__shutdown` 这种**绝对路径**，`file://` 根本没有 host，发不出去；
- 数据是 ~300MB 的 gzip 二进制分片，必须按需 HTTP 取，不能整个塞进页面。

所以 `启动.vbs` 起的是个**只监听 127.0.0.1、不对外、不联网**的 Python 标准库静态服务器，
作用就是把这堆文件用 http 递出去。它没有业务逻辑，也没有数据库。

**不用每次记得点 `停止.vbs`**：服务常驻没有代价（一个空闲 `pythonw.exe`，几个 MB）。
真要收掉有三种方式：页面里的退出按钮（POST `/__shutdown`）、`停止.vbs`、任务管理器。
而且从 Q11 那次修复之后，重复双击 `启动.vbs` 只会复用已经在跑的那个，不会再叠进程。

### S1. 止损止盈新口径（用户口述，逐条落地）

旧口径是死板的「止损 6 点 / 止盈 12 点」。问题：遇到波动大的行情，**刚开单下一根就被扫掉**。

新口径：

| 项 | 规则 |
|---|---|
| 止损 | **前 5 根 K 线的极值外 1 个 tick**（做多 = 最低点 − 0.25；做空 = 最高点 + 0.25） |
| 止盈 | **入场价 ± 2 × 止损距离**（2R） |
